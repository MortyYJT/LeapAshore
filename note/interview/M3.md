## 1. 这一阶段做了什么、为什么

- 问题（`proposal.md` Why）：M1–M2 把档案、选校组合、进度搬到服务端，但「要准备的材料」只有一个勾选框，
  文件无处可放；`review_criteria` 一行都不存在，M4 的 Genuine Student 审核没有落点。M3 接上材料生命周期
  （上传 / 版本 / 归档 / 送审）与带官方来源的审核依据。
- D1 文件本体不进库：**内容寻址**存本地目录 `<root>/blobs/<sha256 前两位>/<sha256>`，版本行只存**相对**
  路径（相对是硬要求，隐私规则禁止绝对路径）。备选：每材料一目录 + 原文件名（要另建去重索引、有路径穿越
  与重名问题）；二进制进库 `bytea`（父设计已否决）。跨主体共享 blob 安全，下载必须过版本行与归属校验（D2）。
  代码 `api/app/services/documents.py:blob_relpath`、`api/app/config.py:Settings.document_storage_root`。
- D3 只收 PDF/PNG/JPEG/DOCX、上限 20 MiB，**按魔数判类型**、不信客户端声明的 Content-Type（否则 HTML 改名
  `.pdf` 存进「已归档」再被当页面取回 = 存储型 XSS），DOCX 还要用 `zipfile` 确认含 `word/document.xml`；
  代码 `documents.py:detect_mime`、`_accept`。D4 写入**先落盘、再写库**，失败模式是孤儿 blob 而不是
  「库里有行、盘上没字节」；限额设两处：`api/app/middleware.py:BodySizeLimitMiddleware` 先返 413，
  `documents.py:_stage` 边搬运边按 64 KiB 计数、超限即中止。D5 版本不可变、`version_no` 从 1 递增、
  `UNIQUE (document_id, version_no)`，并发取号用行锁 `_next_version_no`，撞约束重试一次仍失败 409。
- D6 状态机 `uploaded → archived → under_review → needs_revision / accepted`。三条不显然的规则：送审前必须
  先归档（要点按 `kind` 选）；`under_review` 期间不许重新归档；`insufficient_evidence` 不改状态。代码
  `documents.py:ARCHIVE_ALLOWED_FROM`、`SUBMIT_ALLOWED_FROM`、`archive_document`、`submit_document`。
  D7 循环外键（`documents.current_version_id` ↔ `document_versions.document_id`）手写迁移，建表后用显式
  `op.create_foreign_key` 补上；迁移 `api/alembic/versions/3e76566a439e_*.py` 一次建 5 张表。
- D8 **人工写入走 CLI、HTTP 对审核依据只读**：`api/review_cli.py` 的 `verify-criterion` / `unverify-criterion`
  是全仓库唯一写 `verified_at` 的地方（写 `now()`），`review` 一个事务写结论 + 逐条建议。被否决的替代：
  加共享 token 保护写接口——那是引入一套没有用户的鉴权，token 还会进 `.env`。
- D9 每条建议必须引用一条 criterion（NOT NULL、RESTRICT）；`pass` 不能带 `blocker`，非 pass 至少要有一条
  建议；`scope` 与 `kind` 刻意对齐（`general` 可通用）。后果：`kind` 8 个、`scope` 7 个（没有 `passport`），
  **护照类材料在 M3 里审不了**（种子只写 `gs` 要点）。代码 `reviews.py:_resolve_findings`、`record_review`。
- D10 审核绑定**当前版本**（否则 409）；`run_id` 推迟到 M4；`reviewed_by` NOT NULL。D11 M3 不删任何东西
  （无 DELETE 路由、不做 blob 引用计数）。D12 `task_id`/`program_id` 用 `ON DELETE SET NULL`、`client_id`
  用 CASCADE。D13 关联只有一个方向：`documents.task_id` 权威，`roadmap_tasks.document_id` 与
  `documents.program_id` 保持 NULL。
- D14 前端：`AppShell` 加「材料库」tab 与 `web/components/MaterialsView.tsx`，`FlowView` 任务行加上传
  入口；列表接口只带当前版本、详情才带版本与审核（`api/app/routers/documents.py:read_documents`、
  `read_document`）；来源状态复用 `web/lib/source-status.ts:toSourceStatus`（未知读成「待核验」，绝不读成
  「已核验」）。适配层 `web/lib/materials-source.ts` 绑真实抓取的 `materials-{list,detail}.fixture.json`。
- D15 拆两个 PR（后端 / 前端）、同一个 change；D16 上传字段固定 `file`/`title`/`task_id`，`task_id`
  三种结局互不相同（自己的挂上、别人的 422、任务以后被删则变 NULL）。
- 证据：后端 200 用例、26 条需求逐条映射到代码与检查，`make verify` 在合并后的 main 上退出码 0。计数有
  文档漂移：frontend 验证文档写「前端 172 用例 / 28 张截图」，`note/handoff.md` 与 `note/testing-m3.md`
  写 175 / 29（现有 29 个 PNG，多出的 `29-material-narrow.png` 来自后续修复 `5e8f1f0`）。
- 已知限制：没有删除功能；存储根是本地目录 + Vercel 函数请求体上限约 4.5 MB，**线上不可用**；
  `documents.program_id` 恒为 NULL；护照材料审不了；走查会在 `api/var/documents` 留孤儿 blob；
  「来源已核验」分支没在浏览器里看过；后端测试偶发失败是**既有问题**（main 的 worktree 上把 M3 表降级后
  单跑 `test_applications_api.py` 六次仍有两次失败）。
- 一处文档 / 代码不一致（`待核验`以哪次为准）：frontend 验证文档 §5 说「渲染出来的审核面板没在浏览器里
  看过」，但 HEAD 的 `scripts/e2e-walkthrough.cjs` 里有调真实 CLI 写审核、并渲染 finding / 要点 /
  官方 URL / 状态的步骤与断言。
