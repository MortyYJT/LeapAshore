# 第一部分：设计依据（从界面移出，仅供开发与面试讲解）

界面只回答"我要做什么"。下面这些是"系统为什么这么设计"，属于工程内容，不进 UI。

## 1. 留学申请的状态机

申请这件事本质上是**六个对象在 6–12 个月里被反复修改**：

| 对象 | 是什么 | 谁改 | 可逆性 |
|---|---|---|---|
| 申请档案 | 院校层次、均分、专业、语言、目标、预算 | 用户说 → 系统抽取 | 可随时改 |
| 候选项目池 | 可选项目 + 官方来源 + 版本 | 运营核验后发布 | 有版本历史 |
| 申请组合 | 申哪些、哪个首选 | 用户决定（**需确认**） | 影响后续规划 |
| 路线图 | 从现在到入学的时间安排 | 系统生成 → 用户调整 | 可重算 |
| 任务 | 具体待办 | 系统建议 + 用户自建 | 可改 |
| 知识缺口 | 系统答不上来的问题 | 系统记录 → 人工补源 → 发布 | — |

**关键点**：用户不是一天问完所有问题的。今天问项目要求，下周说考了雅思，下个月决定申请哪几所。
所以这个 Agent 维护的是**一条跨月的状态**，不是一次问答。这也是它与"客服 Agent"最大的区别。

## 2. 意图分流判据

判据不是"消息里有没有这些词"，而是**"这条消息想改变哪个状态"**：

| 意图 | 判据 | 出口 | 是否写 |
|---|---|---|---|
| 规划 / 重规划 | 想改变"申请哪些项目" | 确定性推荐 → 重建路线图 | 写（需确认） |
| 官方要求核验 | 想问某项目的官方要求 | 检索 → 证据门禁 | 只读 |
| 资料补充 | 提供了新的档案事实 | 结构化抽取 → 更新档案 | 写（低风险） |
| 业务操作 | 想改已有决定或任务状态 | 白名单执行器 | 分风险等级 |
| 通用问答 | 以上都不是 | 通用回复 | 只读 |

这样分五类不是拍脑袋——**申请状态总共只有这几种改变方式**。

## 3. 证据门禁（回答前先判断能不能答）

涉及官方要求的回答，四条必须同时满足：

1. 有检索命中（不是模型自己想的）
2. 引用合法（https + 标题 + 来源编号）
3. 来源在有效期内（核验日期不超期）
4. 相关度达到阈值

任一条不满足 → 直接拒答，并记录知识缺口交给人工补来源。
**宁可说"我查不到"，也不给一个用户会照着去申请的错误要求。**

## 4. 写操作分级确认

| 级别 | 操作 | 行为 |
|---|---|---|
| 自动执行 | 更新档案字段、勾选材料、记录截止日期 | 幂等直接落库 |
| 需确认 | 设为首选项目、标记"不考虑"、重算方案（会覆盖已有组合） | 返回提案 → 显式确认 → 执行 |

## 5. 数据诚实性（实现约定）

1. 6 个项目的招生数据全部标 `dataStatus: "待核验"`（`lib/programs.ts`）
2. `SourceCitation.verifiedAt` 为 `null`，**不是任何硬编码日期**
3. 所有时间标 `scheduleOrigin: "suggested"`，界面显示"系统建议 · 非官方日期"
4. 官方截止日期字段留空，界面显示"待核验"
5. 非 985/211 的院校层次（一本/二本/专科）、海外院校 → 一律返回"需要人工核验"，不套用统一基线

## 6. 材料模板与阶段

6 个阶段按入学日期倒推（`lib/roadmap.ts`）：

| 阶段 | 倒推天数 | 说明 |
|---|---|---|
| 锁定申请组合 | 330 | 确定申哪些，标出首选 |
| 学术与身份材料 | 270 | 成绩单、在读证明、评分说明、护照 |
| 语言准备 | 240 | 总分 + **单项**（最常踩的坑） |
| 专项申请材料 | 210 | 简历、陈述、推荐信、作品集、研究计划 |
| 提交申请 | 150 | 逐校提交、保存回执 |
| Offer 与入学 | 60 | 补件、比较 Offer、押金、CoE、签证 |

材料项按学位（研究型/博士 → 研究计划）和方向（设计/艺术 → 作品集）做条件筛选。

## 2026-10-05 — Context7 复核 Tailwind v4，查出一处真实 CSS 层级 bug

### 用户关键原话

- 「我们全程采用superpower+context7的模式。」

### 关键产出与评审结论

- 按 AGENTS.md §1 的要求，用 Context7 复核本项目用到的 Tailwind v4 写法（库 ID `/tailwindlabs/tailwindcss.com`）。官方文档给出三点：
  1. `@import "tailwindcss";` — 与实现一致 ✅
  2. PostCSS 用 `"@tailwindcss/postcss": {}`，且**不需要** `postcss-import` / `autoprefixer`（v4 已内置）— 与实现一致 ✅
  3. **设计变量应放 `@theme` 块**（会同时生成 `bg-brand` 之类工具类），自定义组件类应放 **`@layer components`** — 与实现**不一致** ❌
- **确实的 bug**：自定义组件类写在无层级位置。无层级 CSS 的优先级高于所有 cascade layer，所以 `.card { background: #fff }` 压过了 `bg-[var(--bg-soft)]` 工具类。截图 `04-step5-gpa.png` 可复现：「归一化结果」卡片本该是浅灰底，实际渲染为白色。
- 修复：`app/globals.css` 改为官方结构（`@theme` + `@layer base` + `@layer components`），设计变量重命名为 `--color-*`，并同步更新 7 个组件里的 `var(--...)` 引用。
- 修复后暴露了**原有的设计缺陷**：那张卡片用的 `bg-[var(--bg-soft)]` 与页面底色同为 `#f7f9fa`，一旦层级正确就变得不可见。已在 `Onboarding.tsx:323` 去掉多余的背景工具类，由 `.card` 提供白底。

### 用户拒绝或纠偏

- 本阶段无新增用户指令。

### 翻车与返工

- **库 ID 解析失败两次**：`context7_get_docs("tailwindcss")` 被解析到无关库 `/jamiebuilds/tailwindcss-animate`；`/tailwindlabs/tailwindcss` 返回 301 重定向。最终用 `/tailwindlabs/tailwindcss.com` 成功。**教训：Context7 要用搜索确认库 ID，不要用裸名直接 get_docs。**
- 改完 CSS 后首次复跑，输入的焦点绿边与边框全部变成黑色。误判为样式未生效，实际是 dev server 的 CSS 增量缓存陈旧；`rm -rf .next` 重启后恢复。**教训：改动 `globals.css` 后不能只靠 HMR 判断结果。**
- 我第一轮把 `.card` 与 `bg-*` 工具类叠加使用时没有意识到层级问题，是**靠 Context7 才发现的**——这条正好验证了 AGENTS.md §1「不凭记忆写库 API」这条规则的价值。

## 2026-10-05 — 修悬浮菜单断层，新增头像上传

### 用户关键原话

- 「用户可以自己上传头像，然后你现在这个判定，我点开不了个人中心和设置，一移动到下面就会消失」

### 关键产出与评审结论

- **用户报的是真 bug。** 菜单用了 `top-[calc(100%+6px)]`，那 6px 的缝隙**既不属于按钮也不属于菜单**，
  鼠标经过时触发 `mouseleave`，菜单在指针到达之前就关了 —— 所以「个人信息」和「设置」根本点不进去。
  修法：把缝隙改成菜单外层容器的 `padding-top`，这样那段空间**仍然属于菜单的后代**，不会触发离开。
- 顺手补了两个原本缺失的行为：**点击外部关闭**和 **Esc 关闭**（悬浮菜单否则会一直挂在页面上）。
- **头像上传**：中心裁方 → 压到 256×256 → 以 data URL 存本机 localStorage，**不上传服务器**。
  压缩有两个实际理由：手机原图会撑爆 5MB 配额，非正方形会让人脸在圆形框里变形。
  同时把这条写进了隐私政策，让文档和代码一致。
- **回归测试是验证过有效的，不是写上去好看**：我把菜单临时改回旧的缝隙写法重跑，检查项报「否」；
  改回正确实现报「是」。另外测试用的是**分步移动鼠标**穿过缝隙，而不是直接跳到菜单项上
  —— 后者会绕过这个 bug。

### 用户拒绝或纠偏

- 无。

### 翻车与返工

- 无返工。这轮的两个问题都是用户在实际使用中撞出来的，我自己的截图验收没有发现
  —— **因为我的走查用的是 `locator.hover()`，直接把鼠标瞬移到菜单项，恰好绕开了缝隙。**
  这是这轮最值得记的教训：**验收动作要模拟真实路径（连续移动），而不是跳到终点**。
  同样的道理，之前"渲染正常但 hydration 失败"那一类 bug 也是被这种"跳步验收"漏掉的。
